# Детальний опис проєкту Car Rental Platform

## 1. Загальна ідея та призначення

`Car Rental Platform` - це курсова платформа для автоматизації процесів прокату автомобілів, побудована на мікросервісній архітектурі. Основна мета проєкту - розділити критичні бізнес-напрями на незалежні сервіси, щоб спростити масштабування, підтримку та подальший розвиток функціоналу.

Платформа покриває повний життєвий цикл оренди:

- робота з користувачами та профілями клієнтів/орендарів;
- керування автомобілями, цінами, доступністю та медіа;
- бронювання та орендні процеси;
- фінансова аналітика, штрафи та формування звітів;
- єдина точка входу для фронтенду через API Gateway.

Проєкт перебуває у стані активної міграції та стандартизації: частина сервісів уже є "цільовими", а частина - залишками сумісності для плавного переходу зі старішої моделі.

## 2. Поточна архітектура (runtime-топологія)

### Активна (основна) топологія

У "бойовому" ланцюгу запитів зараз використовуються:

- `api-gateway` (порт `3000`);
- `user-service` (порт `3002`);
- `car-service` (порт `3003`);
- `rental-service` (порт `3004`);
- `media-service` (порт `3006`);
- `reporting-service` (порт `3009`);
- `frontend` (порт `3001`).

### Legacy-сервіси (видалені з репозиторію)

Раніше існували окремі `client-service` та `search-service`. Зараз:

- дані клієнтів/орендарів — у **`user-service`** (міграція з `client_service_db` через `npm run migrate:clients`);
- агрегований пошук **`/api/search/*`** — у **`api-gateway`** (виклики до car / user / rental сервісів).

Окремі процеси на портах `3005` / `3007` для пошуку та клієнтів **не запускаються**.

## 3. Детальна роль кожного сервісу

## `api-gateway`

- Єдина точка входу для фронтенду (`BFF + proxy`).
- Розподіляє запити між внутрішніми сервісами.
- Містить сумісні маршрути для legacy-пошуку (`/api/search/*`).
- Робить rewrite частини legacy-маршрутів (`/api/clients/*`) у напрямку `user-service`.
- Має dev-сумісність для auth (тимчасова поведінка, керується конфігурацією, зокрема `ENABLE_DEV_AUTH`).

## `user-service`

- Володіє доменом користувачів та профілів орендарів/клієнтів.
- Обслуговує дані профілю, документи, рейтинги.
- Є новою ціллю для legacy-клієнтських сутностей.
- Містить міграційний скрипт перенесення даних із `client_service_db`:
  - `npm run migrate:clients` (з кореня репозиторію).
- Має ключові маршрути: `/api/users/*`, `/api-docs`, `/health`.

## `car-service`

- Відповідає за каталог авто, ціноутворення, медіа-метадані, доступність.
- Працює з owner-linked даними автомобілів.
- Основні маршрути: `/api/cars/*`, `/health`.

## `rental-service`

- Реалізує орендні сценарії: бронювання, переходи життєвого циклу оренди.
- Працює з доменними сутностями прокату й пов'язаними штрафами у межах орендного контексту.
- Основні маршрути: `/api/rentals/*`, `/health`.

## `media-service`

- Сервіс завантаження та видачі файлів (зображень).
- Не має власної БД, використовує файлове сховище (локальна директорія/volume).
- Виступає інфраструктурним сервісом для медіа-контенту.

## `reporting-service`

- Відповідає за фінансову аналітику, штрафи, агреговані звіти.
- Обслуговує маршрути:
  - `/api/penalties/*`
  - `/api/reports/*`
  - `/api/analytics/*`
  - `/health`
- Підтримує експорт фінансових звітів:
  - `Excel`: `GET /api/reports/financial/export?format=xlsx`
  - `PDF`: `GET /api/reports/financial/export?format=pdf`
- Використовує `rental_service_db` спільно з `rental-service` (це окремий архітектурний ризик, що потребує чіткої політики ownership).

## 4. Фронтенд та інтеграційна модель

Фронтенд (`React`, директорія `frontend`) працює як єдиний клієнт для бізнес-процесів системи. Він не звертається безпосередньо до кожного сервісу, а використовує `api-gateway` як центральну точку інтеграції:

- базовий API URL: `VITE_API_URL=http://localhost:3000/api`;
- завдяки gateway фронтенд ізольований від внутрішньої топології;
- це спрощує заміну/видалення legacy-сервісів без критичних змін у UI.

## 5. Дані та бази даних

Поточна прив'язка сервісів до БД:

- `user-service` -> `user_service_db`;
- `car-service` -> `car_service_db`;
- `rental-service` -> `rental_service_db`;
- `reporting-service` -> `rental_service_db` (спільне використання);
- колишній `client_service_db` (legacy) — дані переносяться в `user_service_db` через `npm run migrate:clients`.

Ініціалізаційні SQL-скрипти розміщені в `database/init`.

Ключова мета розвитку data layer:

- перейти від `synchronize` до контрольованих міграцій у кожному сервісі;
- формалізувати ownership схем;
- зменшити coupling між сервісами через спільну БД.

## 6. Запуск і верифікація

### Локальний старт

Рекомендований спосіб підняти бекенд:

```bash
docker compose up --build
```

Фронтенд запускається окремо:

```bash
cd frontend
npm install
npm run dev
```

### Сценарії перевірки

У корені workspace визначені скрипти:

- `npm run verify:backend` - перевірка активних backend-сервісів;
- `npm run verify:all` - повна перевірка workspace;
- `npm run verify:frontend` - build фронтенду.

Примітка: у поточному обмеженому середовищі можлива помилка `spawn EPERM` під час frontend build.

## 7. Поточний технічний стан (аудит)

Проєкт уже достатньо зрілий для збірки ключових сервісів, але ще не завершив етап стабілізації. Зафіксовані основні ризики:

1. **Неповна довіра до verification baseline**  
   Частина сервісів має формальні test-скрипти без достатнього покриття сценаріїв.

2. **Неузгодженість документації з фактичним станом**  
   Деякі документи відображають цільовий, а не поточний стан.

3. **Нечіткий lifecycle БД і міграцій**  
   Частина сервісів ще покладається на `synchronize` замість migration-first практики.

4. **Тимчасова логіка в gateway**  
   Наявні dev auth / compatibility блоки, які потрібно або винести в явні режими, або прибрати.

5. **Нерівномірність foundation-практик між сервісами**  
   Різні підходи до логування, валідації конфігурації, обробки помилок.

## 8. Цільова архітектурна модель

Проєкт рухається до спрощеної, але більш стабільної схеми:

- `api-gateway`
- `user-service`
- `car-service`
- `rental-service`
- `reporting-service`
- `media-service`

Ключові архітектурні правила цільового стану:

1. Кожна сутність має один source-of-truth сервіс.
2. Кожен сервіс керує еволюцією схеми через міграції.
3. Gateway залишається BFF/proxy (без зайвої бізнес-логіки).
4. S2S-комунікація стандартизована (таймаути, auth, мапінг помилок).
5. Документація завжди відображає реальний runtime.

## 9. Бізнес-цінність і навчальна цінність проєкту

Як курсова робота цей проєкт демонструє:

- практичне застосування мікросервісної декомпозиції;
- роботу з міжсервісною взаємодією через gateway;
- побудову доменів (users, cars, rentals, reporting, media);
- поєднання транзакційних операцій і аналітичних звітів;
- керовану міграцію legacy-компонентів без зупинки розвитку продукту.

З технічної точки зору, це хороший приклад "живої" архітектури, де система не тільки реалізована, а й проходить через етапи hardening, стандартизації та поступового виведення технічного боргу.

## 11. Проєкт з боку користувача (user perspective)

Цей розділ описує платформу не як набір сервісів, а як продукт, яким користуються люди. Такий підхід зазвичай найзручніший для розділів дипломної "Актуальність", "Постановка задачі", "Аналіз предметної області" і "Опис функціональних вимог".

### 11.1. Яку проблему вирішує система для користувача

У класичному процесі оренди авто користувач часто стикається з такими труднощами:

- незрозуміло, які авто реально доступні на потрібні дати;
- ціна може змінюватися неочікувано або бути непрозорою;
- потрібно довго узгоджувати деталі через дзвінки/месенджери;
- статус бронювання не завжди очевидний;
- історія оренд та супутні платежі (штрафи, фінанси) розпорошені.

Платформа усуває ці проблеми через єдиний цифровий сценарій:

1. користувач знаходить авто за параметрами;
2. оформлює бронювання онлайн;
3. відстежує статус оренди;
4. працює з історією операцій та фінансовими звітами.

### 11.2. Цільові ролі користувачів

У системі є три основні користувацькі ролі.

1. **Клієнт (орендар)**  
   Людина, яка шукає автомобіль, бронює його та керує власними орендами.

2. **Власник/менеджер автопарку**  
   Користувач, який додає авто, керує параметрами, цінами, доступністю та вмістом карток авто.

3. **Адміністратор/аналітик**  
   Користувач, який контролює процеси платформи, переглядає фінансову інформацію, штрафи, аналітику та звіти.

### 11.3. Основні user stories (готово для дипломної)

Нижче наведено приклади user stories, які можна майже без змін використати у тексті дипломної роботи.

- **Як клієнт**, я хочу бачити список доступних автомобілів за заданими датами, щоб швидко знайти релевантний варіант.
- **Як клієнт**, я хочу переглядати детальну картку авто (характеристики, фото, умови), щоб прийняти обгрунтоване рішення.
- **Як клієнт**, я хочу бронювати авто онлайн, щоб не витрачати час на ручні узгодження.
- **Як клієнт**, я хочу бачити статус своєї оренди, щоб розуміти поточний етап виконання послуги.
- **Як власник/менеджер**, я хочу керувати списком автомобілів, щоб підтримувати актуальний каталог.
- **Як власник/менеджер**, я хочу змінювати ціни і доступність, щоб гнучко реагувати на попит.
- **Як адміністратор**, я хочу формувати фінансові звіти у форматах PDF та Excel, щоб проводити облік та аналіз.
- **Як адміністратор**, я хочу контролювати штрафи та фінансові показники, щоб оцінювати ефективність сервісу.

### 11.4. Користувацький шлях (end-to-end customer journey)

Типовий сценарій клієнта в системі:

1. **Вхід у платформу**  
   Користувач переходить у веб-інтерфейс, авторизується або реєструється.

2. **Пошук і відбір авто**  
   Користувач застосовує критерії (дата, клас, характеристики), переглядає результати і порівнює варіанти.

3. **Вивчення деталей автомобіля**  
   Відкриває картку авто, аналізує фото, характеристики, умови оренди, вартість.

4. **Створення бронювання**  
   Обирає період оренди, підтверджує замовлення.

5. **Супровід оренди**  
   Відстежує зміни статусу оренди, взаємодіє з платформою до завершення послуги.

6. **Післяорендний етап**  
   Переглядає історію, фінансові нарахування, за потреби - штрафи чи підсумкові дані.

### 11.5. Яку цінність бачить користувач

З точки зору кінцевого користувача, система дає:

- **прозорість**: видимість доступних авто, цін і статусів;
- **швидкість**: менше ручної комунікації, більше дій онлайн;
- **керованість**: один інтерфейс для повного життєвого циклу оренди;
- **довіру**: фіксація історії операцій і стандартизований процес.

### 11.6. Функціональні вимоги у "людській" формі

Для дипломної зручно формулювати вимоги як перевірювані очікування користувача:

1. Користувач може знайти авто за ключовими параметрами.
2. Користувач може переглянути повну картку автомобіля.
3. Користувач може створити бронювання через веб-інтерфейс.
4. Користувач може відстежувати стани оренди.
5. Оператор/адміністратор може керувати автопарком і даними авто.
6. Адміністратор може формувати та експортувати фінансові звіти.

### 11.7. Нефункціональні вимоги з позиції користувача

Окрім функцій, у дипломі варто зафіксувати очікування до якості сервісу:

- **доступність**: система має бути доступною для щоденного використання;
- **продуктивність**: типові операції (пошук, відкриття сторінок, бронювання) мають виконуватися без помітних затримок;
- **надійність**: дані бронювання і фінансові дані не повинні губитися;
- **безпека**: персональні дані і дії користувача мають бути захищені;
- **масштабованість**: система повинна підтримувати зростання кількості користувачів та операцій.

### 11.8. Готовий фрагмент для розділу "Постановка задачі"

Можна використати таку академічну формулювання:

"Метою розробки є створення інформаційної системи прокату автомобілів, що забезпечує цифрову підтримку повного циклу орендної взаємодії: від пошуку й бронювання транспортного засобу до супроводу оренди та формування фінансово-аналітичної звітності. Система орієнтована на потреби трьох груп користувачів - клієнтів, менеджерів автопарку та адміністраторів, і повинна забезпечувати прозорість процесів, зменшення операційних витрат часу та підвищення керованості сервісу."

### 11.9. Готовий фрагмент для розділу "Практичне значення"

"Практичне значення розробленого рішення полягає у можливості автоматизації ключових бізнес-процесів сервісу прокату автомобілів у межах єдиної веб-платформи. Впровадження системи дозволяє зменшити частку ручних операцій, прискорити обробку звернень клієнтів, покращити контроль орендних і фінансових операцій, а також створити підгрунтя для подальшого масштабування сервісу."
