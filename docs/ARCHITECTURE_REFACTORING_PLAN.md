# Масштабний план рефакторингу та «чистої» архітектури

Документ описує **цільовий стан** коду, **порядок дій** (щоб не зламати робочі сценарії), **бекенд і фронтенд** окремо, **критичні ризики** та **гігієну** (зайвий код, коментарі, legacy). Використовуй як roadmap; конкретні оцінки годин залежать від команди і пріоритетів.

---

## 1. Цілі та обмеження

**Цілі**

- Передбачувана архітектура мікросервісів: один джерело правди на домен, стабільні контракти API.
- Переносимість між середовищами (dev/stage/prod) без «магії» в gateway.
- Єдиний стиль помилок, логів, конфігурації, міграцій БД.
- Фронтенд: зрозумілі шари (API → hooks → UI), менше дублювання, передбачуваний стан і помилки.

**Обмеження (щоб «не поламати нічого»)**

- Зміни робити **інкрементально**: спочатку сумісність (dual-write/read або feature flags), потім видалення legacy.
- Після кожної фази: `npm run verify:backend`, перевірка ключових фронтових сценаріїв (логін, каталог, бронювання, звіти).
- `client-service` / `search-service` вже вилучені з репозиторію; міграція клієнтських даних — через `npm run migrate:clients` на реальних даних перед продакшеном.

## 2. Критичні моменти (P0 — виправити в першу чергу)

| Область | Проблема | Рекомендація |
|--------|-----------|----------------|
| Довіра до тестів | Частина `test`-скриптів формальні; немає сквозних контрактних тестів між сервісами | Ввести мінімальний **contract/smoke** набір (gateway → сервіси) і зафіксувати в CI |
| БД | `synchronize` у dev, не всюди є повний цикл міграцій | Увести **migration-first** для кожного сервісу; узгодити володіння схемою `rental_service_db` між rental і reporting |
| Gateway | Тимчасовий dev-auth, сумісні rewrite-маршрути в одному файлі | Ізолювати в модулі `compat/` або за прапорцями `ENABLE_DEV_*`; документувати, що є тимчасовим |
| Поділ БД | `reporting-service` читає ту саму БД, що й `rental-service` | Документувати політику (read-only replica / окремі view / eventual CQRS) або план розведення |
| Документація | Частина `docs/` описує бажаний, а не фактичний стан | Оновити «джерело правди»: README + SERVICE_CATALOG + цей план; прибрати суперечності |

## 3. Бекенд — що змінити / переробити / додати

### 3.1 Топологія та межі сервісів

**Змінити**

- Чітко зафіксувати **активну** топологію: gateway, user, car, rental, reporting, media.
- Legacy `client-service` / `search-service` видалені з репозиторію; пошук і клієнти — у `api-gateway` + `user-service`.

**Додати**

- Діаграма залежностей (Mermaid у `docs/`) і таблиця «хто кого викликає» з таймаутами та заголовками автентифікації між сервісами.

### 3.2 API Gateway (`services/api-gateway`)

**Змінити / переробити**

- Розбити монолітний `index.ts` на модулі: `routes/search.ts`, `routes/users-compat.ts`, `proxy/*.ts`, `auth/dev.ts`.
- Уніфікувати відповіді пошуку (cars/clients/rentals): однакові поля метаданих пагінації там, де є серверна пагінація.
- Прибрати дублювання логіки парсингу тіл відповідей (`extractArrayPayload` + ad-hoc перевірки) — одна утиліта + типи.

**Додати**

- Валідація query/body (легка схема, напр. zod) на кастомних BFF-ендпоінтах.
- Структуроване логування (request id, маршрут, upstream status).

**Критично**

- Маршрут `GET /api/users/:id` не повинен перехоплювати `GET /api/users/clients` — явно зареєструвати **статичні** шляхи (`/clients`, …) **вище** за `/:id` або винести клієнтів на окремий префікс (узгодити з фронтом).

### 3.3 User Service

**Змінити**

- Завершити роль **єдиного** джерела клієнтів/орендарів; міграція з `client_service_db` — скрипт + верифікація.
- Вирівняти DTO відповіді `listClients` / пошук — стабільна форма для gateway і фронту.

**Додати**

- Повноцінні міграції для всіх змін схеми; вимкнути покладання на `synchronize` у prod.

### 3.4 Car Service

**Змінити**

- Параметри пошуку узгоджені з gateway (`searchQuery`, `page`, `limit`, фільтри) — одна таблиця в `docs/API.md`.
- Репозиторій: пошук за текстом + пагінація — переконатися в індексах (make/model) за навантаженням.

**Додати**

- Тести на DTO/валідацію критичних query.

### 3.5 Rental Service

**Змінити**

- Підняти **jest** у `devDependencies`, якщо в scripts є `test` (усунути невідповідність з аудиту).
- Життєвий цикл оренди, погодження власника, штрафи — чіткі переходи стану в одному місці (state machine або таблиця дозволених переходів).

**Додати**

- Міграції як основний спосіб еволюції схеми.

### 3.6 Reporting Service

**Змінити**

- Явна політика доступу до `rental_service_db` (тільки читання певних таблиць / views).

**Додати**

- Кеш або матеріалізовані агрегати для важких звітів (за потреби).

### 3.7 Media Service

**Додати**

- Обмеження типів файлів, розміру, antivirus hook (опційно), єдиний формат URL для фронту (через gateway).

### 3.8 Спільне для всіх сервісів

**Змінити**

- Єдиний формат помилки: `{ success: false, error: { code, message, details? } }` (або RFC7807 Problem Details).
- Єдиний підхід до env: валідація при старті (напр. `envalid` / zod), fail-fast.
- HTTP-клієнти між сервісами: timeout, retry policy, кореляційний id.

**Додати**

- Health + readiness (`/health`, `/ready` з перевіркою БД).
- OpenAPI актуальність або codegen для внутрішніх клієнтів.

## 4. Фронтенд — що змінити / переробити / додати

### 4.1 Структура та шари

**Змінити**

- Чітке розділення: `services/*` (axios), `hooks/*` (React Query де доречно), `components/*`, `pages/*`.
- Уникати дублювання мапінгу DTO → UI-моделі (авто вже частково через `mapCarFromService` — розглянути спільний `mappers/`).

**Додати**

- Для списків з пагінацією — спільний компонент або хук `usePagedResult` (підпис «Показано X–Y з Z» + Pagination), щоб не копіпастити між вкладками пошуку.

### 4.2 Стан і помилки

**Змінити**

- Узгодити обробку помилок axios (502, зведені `error.detail`) у всіх `search*` hooks.
- Завантаження на вкладках пошуку: один патерн (spinner + empty state).

**Додати**

- За бажанням: React Query для пошуку замість локального стану в `useSearchOperations` — менше ручного керування loading/error.

### 4.3 Типи та API

**Змінити**

- `CarSearchParams`, `RentalSearchParams` тримати синхронізованими з gateway і документацією.

**Додати**

- Типізовані відповіді для пошуку авто з метаданими пагінації (вже частково є — не роздувати дубль типів).

### 4.4 UI/UX гігієна

**Змінити**

- Винести повторювані стилі в тему MUI / спільні `sx` де це вже прийнято в проєкті.

## 5. Чистка коду: коментарі, «зайве», legacy

### 5.1 Коментарі

**Залишити**

- Коментарі там, де **нестандартна бізнес-логіка**, обхід багів бібліотек, неочевидні інваріанти безпеки або міграційні костилі з датою/issue.

**Прибрати / скоротити**

- Коментарі, що дублюють назву функції або очевидний код.
- Великі блоки закоментованого коду — видалити; історія в git.

### 5.2 Мертвий код і дублікати

**Видалити після перевірки**

- Невикористані експорти, старі компоненти після переносу на нові сторінки.
- Дубльовані утиліти (об’єднати в один модуль).

**Не чіпати без аудиту**

- Сумісні маршрути та rewrite в **api-gateway** (`/api/search/*`, `/api/clients/*`, dev-auth тощо), поки на них розраховує фронт або зовнішні клієнти.
- Мапери DTO ↔ UI у фронті, якщо не впевнені, що всі екрани вже на новій формі даних.

### 5.3 Конфігурація та секрети

- Жодних секретів у репозиторії; лише `.env.example` з описом змінних.
- Docker-compose: окремий профіль для «повного» стеку vs «мінімум для фронту».

## 7. Критерії готовності («чиста» архітектура)

- Усі активні сервіси збираються; міграції застосовуються без `synchronize` у prod.
- Gateway не містить «прихованої» логіки без документації; dev-auth вимкненний у prod.
- Репозиторій не містить суперечливих кореневих README щодо топології.
- Фронт: узгоджені патерни помилок і завантаження для основних flows.
- Мінімальний набір e2e або контрактних тестів не «зелений номінально», а реально ловить регресії.
